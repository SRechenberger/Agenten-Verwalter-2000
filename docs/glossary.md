# Glossar

Ein Begriff = eine Bedeutung. Code, Doku und Oberfläche verwenden diese Begriffe konsistent. Englische Bezeichner im Code, deutsche Erklärung hier. Neue Fachbegriffe werden ergänzt, sobald sie abgeklärt sind.

| Begriff | Bedeutung |
|---|---|
| **Vorhaben** | Eine Aufgabe (z. B. „Plan XYZ umsetzen“) mit ihren Repositories, ihrem Workspace und ihren Sessions. Die zentrale Einheit der App. Im Code `project` ([ADR 011](decisions/011-vorhaben-und-sessions.md)). |
| **Gruppe** | Ein benannter Abschnitt der linken Leiste, in den sich Vorhaben einsortieren lassen; ein Vorhaben gehört zu höchstens einer Gruppe. In der Leiste stehen Vorhaben ohne Gruppe oben ohne Kopf, darunter je Gruppe ein Kopf (auch leer); eingeklappt blendet er seine Vorhaben aus und zeigt den dringendsten Status. Löschen einer Gruppe löscht kein Vorhaben, ihre Vorhaben stehen danach ohne Gruppe da. Der Ein-/Ausklapp-Zustand überlebt den Neustart. Ein Vorhaben kommt über sein Menü oder per Ziehen auf die Gruppe hinein und wieder heraus über das Ablegen auf die Fläche „Ohne Gruppe“, das Ablegen auf Zeilen ohne Gruppe oder den Menüpunkt „Ohne Gruppe“; auf der Seite „Neues Vorhaben“ lässt sich die Gruppe schon beim Anlegen wählen oder dort neu anlegen (die Seite startet immer ohne Gruppe). Im Code `ProjectGroup`, Tabelle `project_groups`, Spalte `projects.group_id`. |
| **Übersicht (Vorhaben)** | Hauptansicht eines Vorhabens: TL;DR, Repositories, Sessions, „Neue Session“; Reiter „Übersicht · Changes“. |
| **Host** | Die Instanz, auf der ein Vorhaben liegt und seine Agenten arbeiten. Sie gibt Vorhaben für Gäste frei und kann die Freigabe jederzeit beenden ([ADR 059](decisions/059-remote-sessions.md)). |
| **Gast** | Eine andere laufende Instanz, die über das Netz die Kontrolle über ein freigegebenes Vorhaben des Hosts übernimmt; auf ihr läuft nichts davon. Ein Gast kann mit mehreren Hosts verbunden sein. Im Code ein gekoppeltes Gerät (`DeviceRef`, Tabelle `remote_devices`). |
| **Kopplung** | Der einmalige Schritt, mit dem ein Gast über eine Einladung des Hosts sein Geräte-Token bekommt; danach verbindet er sich damit von selbst, bis der Host das Gerät sperrt. Der Host speichert nur den Hash des Tokens (`remote_devices`), der Gast das Token in `~/.verwalter/remote/hosts.json`. |
| **Einladung** | Der Text `verwalter-remote://<Adresse>:<Port>?fp=…&s=…`, den der Host für eine Kopplung erzeugt: Adresse, Fingerabdruck seines Zertifikats und ein Einmal-Geheimnis. Gilt zehn Minuten und einmal; fünf falsche Geheimnisse machen sie ungültig. Die Adresse ist am Gast änderbar. Im Code `remote::peer::Invitation`. |
| **Freigabe** | Das Angebot des Hosts an alle gekoppelten Geräte, ein Vorhaben zu übernehmen. Überlebt den Neustart. Ohne Übernahme arbeitet der Host normal weiter. „Freigabe beenden“ ist zugleich das Herauswerfen. Im Code `projects.remote_shared`. |
| **Übernahme** | Ein Gast wird Inhaber eines freigegebenen Vorhabens; es gibt je Vorhaben höchstens einen. Der Host liest solange nur mit (`CommandError::ControlledBy`). Sie endet mit „Zurückgeben“, dem Ende der Freigabe, dem Sperren des Geräts, dem Ausschalten des Servers, dem Neustart des Hosts oder nach fünf Minuten ohne Verbindung. Im Code `remote::control`, nur im Speicher; am Gast `remote_take` und `remote_give_back`. Am Gast erscheinen Sessions, Umsetzungen und Überschneidungen eines Vorhabens nur, solange er es übernommen hat. |
| **Marke** | Das Zeichen ⇄ hinter dem Namen eines Vorhabens in der Leiste: am Host „für Gäste freigegeben“ oder „ein Gast steuert“, am Gast „läuft auf <Host>“. Die Meta-Zeile nennt dazu den Host (Gast) oder den Zustand der Freigabe (Host); die Zeile behält ihre Höhe, einen Knopf hat sie nie. |
| **Sperrzeile** | Die gestrichelte Zeile statt der Eingabeleiste, solange ein Vorhaben gesperrt ist: am Host „Gesteuert von <Gerät>. Du liest mit.“ (nach einem Abriss „Reserviert für …“, mit Restzeit in einem Band darüber), am Gast „Host nicht erreichbar“ samt erhaltenem Entwurf. Gesperrt sind auch alle anderen Bedienelemente, die ins Vorhaben schreiben (`useProjectLocked`). |
| **Angebot** | Ein Vorhaben eines Hosts, das der Gast nicht übernommen hat. Die Leiste zeigt „Frei · <Host>“, die Hauptfläche „Übernehmen“; Sessions und Verlauf gibt es erst nach der Übernahme. |
| **Herkunft** | Der Name des Geräts, von dem eine Nachricht oder die Antwort auf eine Rückfrage kam (`ChatEntry::User.origin`, `ChatEntry::Question.origin`). Der Server des Hosts trägt ihn ein; `None` heißt: die eigene Oberfläche. Der Agent sieht ihn nie. |
| **Host-Profil** | Betriebsart, Modelle und Skill-Aufrufe des Hosts (`HostProfile`), die ein Gast für Vorhaben dieses Hosts anzeigt statt seiner eigenen. |
| **Fernsteuerung** | Oberbegriff für alles, womit ein Gast ein Vorhaben des Hosts steuert. Eingerichtet wird sie im Abschnitt „Fernsteuerung“ der Einstellungen (Kategorie „App“): am Host „Gäste erlauben“, Port, Status mit Adressen und Fingerabdruck, „Einladung erstellen“ und die Geräteliste mit „Sperren“; am Gast die Liste der verbundenen Hosts mit „Trennen“ und „Vergessen“ und das Formular „Weiteren Host verbinden“. Ohne den Schalter lauscht der Verwalter auf nichts. |
| **Session** | Eine Claude-Session innerhalb eines Vorhabens, mit eigenem Agenten, Chat, Kontext und Events; im Vorhaben durchnummeriert (#1, #2 …). Ihre ID ist die Session-ID der Claude-Kommandozeile. |
| **Browser-Zugriff** | Schalter pro Session, der den Agenten mit Claude in Chrome startet (`--chrome`); der Agent bedient dann den echten Chrome des Users mit dessen Anmeldungen. Nur im Claude-Betrieb. Im Code `chrome` ([ADR 030](decisions/030-browser-zugriff.md)). |
| **TL;DR** | Kurzfassung einer Session bzw. eines Vorhabens in drei, vier Zeilen, per Knopf von Haiku erstellt; zeigt, wie viele Einträge seither dazugekommen sind. Im Code `tldr` ([ADR 011](decisions/011-vorhaben-und-sessions.md)). |
| **Retro** | Rückblick über alle Sessions eines Vorhabens: der Verwalter sammelt je Session Befunde (Mini-Retro), der Skill `session-review` wertet sie in einer neuen Session aus. Im Code `retro` ([ADR 028](decisions/028-vorhaben-retro.md)). Dazu je Session eine Werkzeug-Retro mit Haiku ([ADR 067](decisions/067-werkzeug-retro.md)). |
| **Regel-Spur** | Was eine Session über die Regeln des Nutzers verrät: geladene Skills und Hook-Sperren; steht in den Retro-Dateien ([ADR 053](decisions/053-regel-spuren.md)). |
| **Mini-Retro** | Rohbefunde einer Session aus einem Einmal-Aufruf mit Sonnet, ohne Bewertung; alle zusammen ergeben `befunde.md` im Retro-Ordner des Workspace. |
| **Werkzeug-Spur** | Die Werkzeug-Aufrufe einer Session je Nutzer-Auftrag, normalisiert und ohne Modell verdichtet; `spur-<N>.md` im Retro-Ordner ([ADR 067](decisions/067-werkzeug-retro.md)). |
| **Werkzeug-Retro** | Einmal-Aufruf mit Haiku je Session über die Werkzeug-Spur: Ziel, Weg, feste Handgriffe, Reibung, Zweck der Inline-Skripte; steht in `werkzeuge.md`. |
| **Repository** | Ein lokales Git-Repository, das in der App bekannt ist (Name, Pfad, Remote). Existiert unabhängig von Sessions. Die App kennt es, sobald es einmal über „Repository hinzufügen“ gewählt wurde; gespeichert ist der Wurzelordner. Auch ein Ordner ohne Git (→ Ordner ohne Git). |
| **RepositoryWorkspace** | Die Verbindung eines Repositorys mit einem Vorhaben: Haupt-Checkout und Basis, für alle Sessions des Vorhabens gleich; bei Sessions vor ADR 010 ein eigener App-Worktree mit Branch. |
| **Worktree** | Ein zusätzliches Arbeitsverzeichnis eines Git-Repositorys mit eigenem ausgecheckten Branch (`git worktree`). Seit ADR 010 legt ihn der Agent an (→ Ticket-Worktree); Sessions davor haben je Repository einen von der App angelegten. |
| **Repository anhängen** | Nimmt ein bekanntes Repository nachträglich in ein Vorhaben auf („+ Repository“ in der Übersicht); gilt für alle seine Sessions. Die Basis der Changes ist der letzte Commit vor dem Anlegen des Vorhabens. |
| **Haupt-Checkout** | Der Ordner, in dem ein Repository auf dem Rechner liegt, mit seinem ausgecheckten Branch — im Gegensatz zu einem Worktree. |
| **Inneres Repository** | Ein Git-Repository direkt in einem angehängten Repository oder Ordner ohne Git (Unterordner mit `.git`-Ordner, eine Ebene tief). Seine Ticket-Worktrees `<Name>-wt-*` liegen daneben im angehängten Ordner. Die Changes zeigen es als `<Repository>/<Name>`, sobald die Reichweite darin etwas committet oder geschrieben hat ([ADR 020](decisions/020-innere-repositories.md)). |
| **Ordner ohne Git** | Ein bekannter Ordner ohne `.git`. Der Agent arbeitet darin wie im Haupt-Checkout; die App hat dort keine Basis, zeigt für den Ordner selbst keine Changes, wohl aber für seine inneren Repositories, und kann nichts zurückholen. Laufwerke, der Benutzerordner und alles darüber sowie der Datenordner der App sind gesperrt. Im Code `RepositoryKind::Folder` / `RepositoryCheckout::Folder` ([ADR 018](decisions/018-ordner-ohne-git.md)). |
| **Ticket-Worktree** | Ein Worktree, den der Agent nach seinen Anweisungen neben dem Haupt-Checkout anlegt, Ordner `<repo>-wt-<Name>` — bei einem inneren Repository im angehängten Ordner (→ Inneres Repository). Die Changes erkennen ihn auch ohne diesen Namen und an anderer Lage (etwa innerhalb des Repository-Ordners), sobald die Session darin eine Datei geschrieben hat: an der `.git`-Datei seiner Wurzel. Er gehört zum Vorhaben, sobald der Agent einer seiner Sessions ihn benutzt hat, und erscheint in den Changes der Session, die ihn benutzt hat, und in der Vorhaben-Übersicht; gemessen gegen den Standard-Branch mit den eigenen Commits (ADR 010, ADR 014). |
| **Session-Branch** | Der Branch `verwalter/<Name>`, den die App für Sessions vor ADR 010 in jedem ihrer Repositories angelegt hat; in allen Repositories einer solchen Session gleich. Neue Vorhaben bekommen keinen: Branches legt der Agent nach seinen Anweisungen an. |
| **Einstellungen** | Werte, die für die ganze App gelten: Farbschema, Betriebsart und lokales Modell sowie die Standardwerte: Modell und Denkaufwand nehmen alle neuen Sessions, auch in einem bestehenden Vorhaben, den Modus die erste Session eines neuen Vorhabens (weitere erben ihn). Gespeichert in der Tabelle `settings` ([ADR 012](decisions/012-einstellungen-farbschema-und-listen.md)). |
| **Betriebsart** | Woher der Agent sein Modell bekommt, für die ganze App in den Einstellungen: Claude (Claude-Abo), Claude Code + LM Studio (dieselbe Claude-Kommandozeile, Modell lokal in LM Studio), Autark (eigener Agent des Verwalters, ohne Claude-Kommandozeile und ohne Anthropic) oder Codex (OpenAI Codex mit dem ChatGPT-Konto). Nicht zu verwechseln mit dem Modus einer Session ([ADR 016](decisions/016-betriebsarten-und-lokales-modell.md), [ADR 017](decisions/017-autarker-agent.md), [ADR 031](decisions/031-codex.md)). |
| **Codex** | Die Betriebsart, in der die Sessions mit OpenAI Codex und dem ChatGPT-Konto des Benutzers arbeiten statt mit Claude; Codex führt seine Verläufe selbst ([ADR 031](decisions/031-codex.md)). |
| **Übersetzer** | Der Unterbefehl `codex` von `verwalter.exe`: spricht nach außen das Zeilenprotokoll der Claude-Kommandozeile, nach innen mit `codex app-server` — so bleibt der Rest des Verwalters für „Codex“ unverändert ([ADR 031](decisions/031-codex.md)). |
| **Autarker Agent** | Der eigene Agent des Verwalters für die Betriebsart Autark: gleiche Werkzeugnamen wie Claude Code, Modell aus LM Studio, Subagenten, Hintergrundprozesse, MCP-Server und Web ohne Anthropic ([ADR 017](decisions/017-autarker-agent.md)). |
| **Lokales Modell** | Ein in LM Studio geladenes Sprach- oder Bildmodell, das in den Betriebsarten Claude Code + LM Studio und Autark die Modellanfragen beantwortet; gewählt in den Einstellungen. |
| **Farbschema** | Dunkel, Hell oder System (folgt Windows); gilt für Inhalt und Titelleiste, gespeichert in den Einstellungen. |
| **Workspace** | Der Arbeitsordner eines Vorhabens; alle seine Sessions teilen ihn. Hier liegen Anhänge (bei Sessions vor ADR 010 auch die App-Worktrees). Arbeitsverzeichnis und Sicherheitsgrenze des Agenten. Liegt unter `<Benutzerordner>\.verwalter\workspaces\<8 Zeichen>`; ändert sich für ein Vorhaben nie. |
| **Workspace Contract** | Die feste Ordnerstruktur, die der Agent sieht: ein Unterordner pro Repository, sonst nichts. |
| **Base ref** | Der Branch, der beim Anlegen der Session im Haupt-Checkout ausgecheckt war (bei losgelöstem HEAD die Commit-ID); angezeigt als „gegen <Basis>“. Gemessen wird gegen `base_commit`, die Commit-ID dieses Stands. Pro RepositoryWorkspace. Bei einem nachträglich angehängten Repository ist `base_commit` der letzte Commit vor dem Anlegen des Vorhabens. |
| **Committed / Uncommitted** | Änderungen seit der Basis, die bereits als Commit im Session-Branch liegen bzw. nur im Arbeitsverzeichnis (gestagte und untracked Dateien eingeschlossen). Gezählt wird nur, was der Session bzw. dem Vorhaben gehört (ADR 014). |
| **Blickwinkel** (`ChangeScope`) | Welche Änderungen die Changes-Ansicht zeigt: „Alle“ (Basis → Arbeitsverzeichnis), „Uncommitted“ (letzter Commit → Arbeitsverzeichnis, samt gestagten und neuen, nicht ignorierten Dateien), „Committed“ (Basis → letzter Commit). In der Oberfläche das Segment „Alle · Uncommitted · Committed“. |
| **Eigene Changes** (`ChangesReach`) | Was die Changes-Ansicht zeigt: in einer Session nur ihre eigenen Commits und die Dateien, die ihr Agent geschrieben und seitdem nicht committet hat; in der Vorhaben-Übersicht die Summe aller Sessions. Eigene Commits erkennt die App am Zeitfenster der Git-Befehle des Agenten (ADR 014). |
| **Fremde Änderung** | Eine uncommittete Datei im Ordner eines Eintrags der Changes, die nicht zu den eigenen Changes der Session gehört — von Hand, von einer anderen Session oder von einem Programm geändert. Die Git-Werkzeuge zeigen sie getrennt und haken sie nicht von selbst an ([ADR 025](decisions/025-git-werkzeuge.md)). |
| **Verlauf (Git)** | Die letzten 50 Commits des ausgecheckten Branches als Graph in der Übersicht der Changes, dazu die eingehenden Commits aus dem Upstream (`HEAD..<Upstream>`) als eigene Zeile. Nur der aktuelle Branch; eingehende Commits sind so aktuell wie der letzte Fetch ([ADR 025](decisions/025-git-werkzeuge.md)). |
| **Sperre (Git)** | Git-Befehle, die Dateien im Arbeitsordner ändern (Branch wechseln, Pull, Verwerfen, Stash, Merge, Rebase), warten, solange eine Session des Vorhabens arbeitet (`Starting`, `Running`, `Waiting`) — alle Sessions eines Vorhabens teilen die Ordner. Commit, Push und Fetch bleiben frei ([ADR 025](decisions/025-git-werkzeuge.md)). |
| **Agent** | Der externe Coding-Agent-Prozess (z.B. Claude), der in einer Session arbeitet. Die App orchestriert ihn, ist aber nicht selbst der Agent. |
| **Provider** (`AgentProvider`) | Adapter, der einen bestimmten Agenten-Typ startet, steuert und seine Ausgaben in einheitliche Agent-Events übersetzt (Claude, später OpenCode, LM Studio). |
| **Agent-Event** | Ein strukturiertes Ereignis aus dem Agentenlauf oder der App (z.B. `tool.started`, `session.waiting`). Wird im Event Store gespeichert und von der UI in lesbare Zustände übersetzt. |
| **Event Store** | Ursprünglich als Tabelle `events` mit allen Zustandsänderungen einer Session gedacht. Umgesetzt ist er als Tabelle `chat_entries`: eine Zeile je Chat-Eintrag, wie ihn die Oberfläche anzeigt; rohe Agent-Ereignisse werden nicht gespeichert ([ADR 004](decisions/004-persistenz-und-wiederherstellung.md)). |
| **Session-Status** | Zustand einer Session, acht Werte: `starting` (Prozess gestartet, noch kein `system/init`), `running` (Agent arbeitet an einer Antwort), `waiting` (offene Rückfrage oder Rechte-Abfrage), `paused` (nach Pause/Esc, nach „Agent neu starten“ oder nach einer Antwort am aufgebrauchten Kontingent), `completed` (Antwort fertig, Agent wartet auf die nächste Nachricht), `cancelled` (abgebrochen, nimmt keine Nachrichten mehr an), `error` (Prozess unerwartet beendet oder Antwort mit einem anderen Fehler), `new` („Neu“: Session im Vorhaben angelegt, Agent nie gestartet, kein Verlauf; startet mit der ersten Nachricht). Eine Unterbrechung ist immer `paused`. Arbeitet der Agent in `completed` oder `paused` von selbst weiter (nach dem Ende eines Subagenten oder Hintergrundprozesses), wechselt die Session auf `running`. Nach einem App-Neustart ist eine vorher aktive Session (`starting`, `running`, `waiting`) `paused`; ihr Agent startet mit der nächsten Nachricht neu; `new` bleibt `new`. |
| **Waiting** | Der Agent hat eine Rückfrage oder Rechte-Abfrage gestellt und wartet auf eine Antwort im Chat. Eigener Status, prominent in der Session-Liste. |
| **Wartet auf Skript** | Anzeige-Status der Sidebar, kein Session-Status: der Agent hat abgegeben (`Completed`), kein Subagent wartet, und mindestens ein Hintergrund-Befehl (`Process`) ohne erkannte lokale Adresse läuft noch. Der Agent setzt fort, sobald er endet. Ein Dev-Server mit Adresse zählt nicht ([ADR 032](decisions/032-wartet-auf-skript.md)). |
| **Letzte Aktivität** | Zeitpunkt, an dem der User zuletzt gesendet oder der Agent zuletzt abgegeben hat — Rückfrage, fertig oder Fehler. Werkzeug-Aufrufe zählen nicht. Bestimmt die Reihenfolge in der Sidebar ([ADR 019](decisions/019-letzte-aktivitaet-und-ungelesen.md)). |
| **Ungelesen** | Eine Session, deren letzte Aktivität jünger ist als der letzte Blick des Users. Gesehen ist eine Session, solange sie im Chat- oder Changes-Reiter offen ist, an der eigenen Oberfläche oder an der eines Gastes ([ADR 059](decisions/059-remote-sessions.md)). |
| **Archivieren** | Blendet ein Vorhaben samt aller seiner Sessions aus der Liste aus (`archived_at` in der Datenbank gesetzt); einzelne Sessions lassen sich nicht archivieren. Der Verlauf bleibt erhalten; bei Sessions vor ADR 010 entfernt die App App-Worktrees ohne offene Änderungen; Haupt-Checkouts und Ticket-Worktrees bleiben immer. Archivierte Vorhaben findet der Archiv-Dialog über Namen und Chat-Text ([ADR 029](decisions/029-archiv-suche.md)). |
| **Wiederherstellen** | Holt ein archiviertes Vorhaben samt aller seiner Sessions aus dem Archiv zurück in die Seitenleiste (`archived_at` wieder leer). Der Verlauf lädt beim Öffnen einer Session, der Agent startet erst mit der nächsten Nachricht; abgebrochene Sessions sind danach wieder schreibbar. |
| **Rückfrage** | Frage des Agenten mit Optionen (AskUserQuestion); mehrere Fragen erscheinen als Ziehharmonika, nur die aktive ist aufgeklappt ([ADR 045](decisions/045-rueckfrage-kasten.md)). |
| **Notiz (Rückfrage)** | Kurzer Text zu einer Option einer Rückfrage; geht als `<Option> (Notiz: <Text>)` an den Agenten ([ADR 045](decisions/045-rueckfrage-kasten.md)). |
| **Eigene Antwort (Rückfrage)** | Freitext zu genau einer Frage einer Rückfrage; ersetzt bei Einfachauswahl die Wahl ([ADR 045](decisions/045-rueckfrage-kasten.md)). |
| **Rechte-Abfrage** | Der Agent fragt vor einem Werkzeug-Aufruf um Erlaubnis; erscheint im Chat wie eine Rückfrage mit Erlauben/Ablehnen. |
| **Tool-Aktivität** | Die Einzelschritte des Agenten (Datei lesen, Befehl ausführen …). Im Chat standardmäßig eingeklappt zusammengefasst. |
| **Chat-Ansicht** | Hauptansicht einer Session: Gespräch mit dem Agenten, Status, Rückfragen. |
| **Zeitpunkt (Eintrag)** | Wann ein Eintrag im Chat entstand, in Millisekunden seit 1970. Im Core `ChatEntry::at()`: das Feld `at` der Einträge, bei Nutzer- und Session-Nachrichten `sent_at`; `push_entry` stempelt ihn einmal, Ersetzen und Ändern an Ort und Stelle behalten ihn. Einträge von vor dem Feld haben keinen, die Oberfläche zeigt dann nichts ([ADR 069](decisions/069-zeitpunkt-im-chat.md)). In der Oberfläche steht nur die Uhrzeit links über dem Eintrag (Nachrichten immer, sonst beim Überfahren), der Tooltip nennt den vollen Zeitpunkt. |
| **Tagestrenner** | Die Zeile „Heute, Sonntag 15.11.“ oben im Block-Rahmen des Verlaufs, wenn der Tag gegenüber dem letzten Block mit Zeitpunkt wechselt. Der erste Block mit Zeitpunkt bekommt keinen, solange ältere Einträge nachzuladen sind. Kein eigener Block der Liste. Blöcke ohne Zeitpunkt bekommen keinen und unterbrechen keinen Tag. |
| **Changes-Ansicht** | Prüfansicht eines Vorhabens, erreichbar aus jeder seiner Sessions: die eigenen Änderungen (Session) bzw. die aller Sessions (Vorhaben-Übersicht): Repositories, Dateien und Diffs gegen die Basis, im gewählten Blickwinkel. |
| **Artefakte-Ansicht** | Ansicht eines Vorhabens, erreichbar aus jeder seiner Sessions und der Übersicht: Liste der Artefakte und Vorschau der gewählten Seite; erscheint erst mit dem ersten Artefakt. |
| **Review-Kommentar** | Kommentar zu einer Diff-Zeile, einem Element eines Artefakts oder einem Bereich auf einem Bild; wird in der Eingabeleiste gesammelt und mit der nächsten Nachricht an den Agenten geschickt. Im Code `ReviewComment` mit Ziel `CommentTarget` ([ADR 015](decisions/015-changes-review.md), [ADR 035](decisions/035-kommentare-artefakt-bild.md)). |
| **Lücke** | Unveränderte Zeilen zwischen zwei Änderungen einer Datei, vor der ersten und nach der letzten, als grauer Balken im Diff, aufklappbar: ein Pfeil blendet bis zu 20 Zeilen an seiner Seite ein, der Text im Balken die ganze Lücke, „Ganze Datei“ im Dateikopf alle Lücken („Nur Änderungen“ klappt sie wieder zu). Eingeblendete Zeilen tragen Nummern, Farben und Review-Kommentare wie jede Diff-Zeile. Im Code `gap` ([ADR 043](decisions/043-unveraenderte-zeilen.md)). |
| **Gesammelte Kommentare** | Die noch nicht gesendeten Review-Kommentare einer Session; flüchtig wie der Entwurf, gehen beim Neustart der App verloren. Ihre Zahl steht am Reiter „Chat“. |
| **Bildansicht** | Großansicht eines Bild-Anhangs; dort lassen sich Bereiche kommentieren ([ADR 035](decisions/035-kommentare-artefakt-bild.md)). |
| **Dateiverweis** | Pfad in einer Agenten-Antwort (als Inline-Code oder Markdown-Link), der per Klick mit dem Standardprogramm von Windows öffnet. Nur Anzeige-Formate (HTML, PDF, Bilder, Markdown, Text) und nur innerhalb des Vorhabens; was scheitert, steht in der Fehlerleiste der Session ([ADR 023](decisions/023-dateiverweise-im-chat.md)). |
| **Anhang** | Bild oder Datei, die mit einer Nachricht an den Agenten geht (per Knopf, Hineinziehen oder Einfügen). Liegt nach dem Senden unter `<Workspace>\.anhaenge\`; Bilder bis 3,75 MiB und PDFs bis 10 MiB gehen als Inhalt an den Agenten, alles andere als Pfad. |
| **Skill** | Eine benannte, wiederverwendbare Arbeitsanweisung für den Agenten, aufgerufen als Nachricht, die mit `/name` beginnt. Das `/`-Menü zeigt Skills und Befehle aus `~\.claude\skills`, `~\.claude\commands` und denselben Ordnern der Repositories einer Session; dazu im Abschnitt „Mitgeliefert“ die mitgelieferten Befehle der Betriebsart (ADR 034). Das `/`-Menü sortiert Skills nach Aufrufen der letzten 30 Tage (ADR 039). |
| **Befehl** (Command) | Eine Markdown-Datei in `.claude\commands`, aufgerufen wie ein Skill mit `/name`. |
| **Mitgelieferter Befehl** | Ein `/name`, das der Agent der Betriebsart selbst versteht, ohne Datei: in „Claude“ und „Claude + LM Studio“ die Liste der Kommandozeile; „Autark“ und „Codex“ haben keinen. |
| **Modus** | Wie selbstständig der Agent arbeitet: Manuell, Automatisch bearbeiten, Planen, Auto. Pro Session, jederzeit wechselbar. |
| **Denkaufwand** | Wie gründlich das Modell nachdenkt, fünf Stufen von Niedrig bis Max. Pro Session, jederzeit wechselbar: im Modell-Menü, im Modus-Menü und im `/`-Menü. |

Im Code `Notice::QuotaExhausted`; nur im Claude-Prozess ([ADR 051](decisions/051-kontingent-warnung.md)). |

Angezeigt im Abschnitt „Konto“ der Einstellungen; gilt für jeden Agenten, der danach startet ([ADR 021](decisions/021-claude-konto.md)). |

Ein Server mit Status „Fehlgeschlagen“ oder „Anmeldung nötig“ zählt als Problem und erscheint als Hinweis in der Eingabeleiste ([ADR 013](decisions/013-mcp-server-im-dialog.md)). |

Gestellt im **Fenster** über der Eingabeleiste (`/btw`, Zeile im `+`-Menü, `Strg+;`), gesammelt im **Reiter** „Nebenfragen“ des Hintergrund-Panels (höchstens 20 je Session, nach dem Beenden der App weg). Im Code `side` ([ADR 044](decisions/044-nebenfragen.md)). |

Eigene Server verbinden sich nach der Anmeldung von selbst, claude.ai-Connectoren nach „Neu verbinden“. Bis die Liste den Server anders meldet oder der Agent endet, gilt die Anmeldung als offen ([ADR 024](decisions/024-mcp-anmeldung.md)). |
| **Hilfsprozess** | Ein kurz gestarteter `claude.exe` (bzw. `codex app-server`), der nur eine einzige Abfrage beantwortet (Kontingent, bei Codex auch Konto und Modelle) und sich danach beendet; gehört zu keiner Session. |
| **Diktieren** | Sprache per Mikrofon aufnehmen und lokal in Text für den Entwurf umwandeln; sendet nie selbst. Im Code `voice` ([ADR 009](decisions/009-sprachdiktat-lokal.md)). Abschnitt — ein Stück der Aufnahme zwischen zwei Sprechpausen, das einzeln erkannt wird. Bedienung: Klick auf das Mikrofon in der Textzeile oder `Strg+M` startet, derselbe Weg beendet; der Text erscheint satzweise schon während des Sprechens an der Cursorstelle, Feld und Senden sind bis zum Ende gesperrt, Esc verwirft das ganze Diktat. |
| **Sprachmodell** | Die lokal gespeicherten Parakeet-Dateien unter `<Benutzerordner>\.verwalter\models\parakeet-tdt-0.6b-v3\`, die das Diktieren braucht; werden einmal auf Klick geladen (rund 670 MB), danach läuft die Erkennung ohne Internet. |
| **Core** | Der Rust-Teil der App (`src-tauri/`): Prozesse, Git, Datenbank, Dateisystem. Die React-Oberfläche spricht nur über Tauri Commands und Events mit ihm. |
| **Session-Werkzeuge** | Die vier Werkzeuge des Verwalters im MCP-Zugang, mit denen Sessions eines Vorhabens miteinander sprechen: `verwalter_send_message_to`, `verwalter_get_sessions`, `verwalter_get_session_tldr`, `verwalter_open_session`. Nur in der Betriebsart Claude. Im Code `session_tools`. |
| **Selbstfreigabe** | Werte je Vorhaben: „Selbstfreigabe für Nachrichten“, „für TL;DR“, „für neue Sessions“ lassen das jeweilige Session-Werkzeug ohne Kasten laufen, dazu das Modell des TL;DR. Standard für neue Vorhaben aus den Einstellungen: alles aus, Haiku. Einstellbar in der Übersicht des Vorhabens, als Standard in den Einstellungen und je Art über den Schalter „Künftig ohne Nachfrage“ im Kasten; der offene Kasten bleibt dabei offen. Die Kettenbremse `CHAIN_LIMIT` holt den Kasten bei Nachrichten und neuen Sessions zurück, er zeigt dann „6 selbst freigegebene Aufrufe in Folge“. Nicht zu verwechseln mit dem Modus `Auto` einer Session. Im Code `SelfRelease`. |
| **Session-Nachricht** | Nachricht einer anderen Session im Chat, mit Absender (Nummer, Titel, ID) statt als Nachricht des Nutzers. Die Oberfläche zeigt sie wie eine Nutzernachricht unter dem Kopf „Von Session <Nummer> „<Titel>““, der in die Session springt, solange sie in der Liste steht. Der Agent bekommt sie mit der vom Core gesetzten ersten Zeile `[Nachricht von Session <Nummer> „<Titel>“, ID <uuid>]`. Ruht das Ziel nicht oder wartet dort schon eine, wartet sie in `session_inbox`. Im Code `ChatEntry::SessionMessage`. |
| **Übergabe** | Von Haiku aus dem Gesprächstext einer Session geschriebene Zusammenfassung, die der Knopf im Hinweis bei kaltem Cache in den Entwurf der Folgesession setzt; ohne Haiku ein Auszug aus erster Nachricht und letzten Beiträgen ([ADR 054](decisions/054-uebergabe-bei-kaltem-cache.md)). Nicht zu verwechseln mit der Einstiegszeile, die der Agent selbst schreibt. |
| **Einstiegszeile** | Eine Zeile „Neues Vorhaben … : …“ in einer Agenten-Antwort (Auftrag für ein neues Vorhaben; erkannt in den letzten fünf nicht leeren Zeilen und weiter oben außerhalb von Code-Blöcken); eine Antwort darf mehrere tragen. Die Sidebar zeigt die abgeschlossene Session dann als „wartet auf Wiedereinstieg“; „In neuem Vorhaben starten“ öffnet „Neues Vorhaben“ vorbelegt. Die Zeilen „Weiter: …“ und „Zurück an …“, die Eltern-Session und der gleichnamige Schalter „Automatisch weiter“ dieser Zeilen sind entfallen (nicht der Schalter einer Umsetzung, siehe **Automatisch starten**); solche Zeilen sind normaler Text, an ihre Stelle treten die Session-Werkzeuge ([ADR 052](decisions/052-session-werkzeuge.md), [ADR 027](decisions/027-session-uebergabe.md)). |
| **Automatisch fortsetzen** | Schalter an einer Session, die wegen eines aufgebrauchten Kontingents **Pausiert** ist (Standard aus, braucht eine bekannte Rücksetzzeit): 30 Sekunden nach dem Zurücksetzen schickt der Verwalter dieser Session selbst die Aufforderung, weiterzumachen. Der Zeitgeber und der Schalter der Session leben nur im Speicher ([ADR 051](decisions/051-kontingent-warnung.md)). Für eine **Umsetzung** ist der Wert gespeichert: an der Umsetzung (Feld `auto_resume`, Befehl `implementation_set_auto_resume`) und je **Station** (leer = wie die Umsetzung, an, aus; Befehl `implementation_set_station_auto_resume`; wirksam ist `resumes_automatically`, Station vor Umsetzung); eine neue Umsetzung übernimmt den Standardwert aus den Einstellungen (`default_auto_resume`, aus). Die letzte Aktion gewinnt: Der Schalter der Umsetzung setzt alle nicht fertigen Stationen auf „wie die Umsetzung“, die Karte im Chat einer Station schreibt den Wert dieser Station. Eine neue Kontingent-Pause einer Station schaltet den Zeitgeber nur scharf, wenn der wirksame Wert an ist und die Rücksetzzeit bekannt ist und in der Zukunft liegt; Rückfragen, die anlegende Session und Sessions außerhalb einer Umsetzung beginnen jede Pause mit „aus“. Eine angenommene Station setzt nie fort: Die Annahme beendet ihren Zeitgeber, und beim Feuern wird es noch einmal geprüft. Nur der Benutzer setzt den Wert, kein Werkzeug. In der Oberfläche: Schalter „↻ Automatisch fortsetzen“ in der Leiste der Umsetzung und in der **Warnleiste**, ↻ in der Zeile einer Station (ein Punkt daran zeigt eine Abweichung von der Umsetzung), die Wahl „wie Umsetzung · an · aus“ im Abschnitt **Automatik** der **Kartei** und eine Zeile in den Einstellungen (Kategorie Agent, gilt nur für neue Umsetzungen) ([ADR 064](decisions/064-automatisch-fortsetzen.md)). |
| **Setzt automatisch fort** | Zustand einer **Station** (`waitsForQuota`): Ihre Session ist am Kontingent pausiert und der Zeitgeber von **Automatisch fortsetzen** ist scharf. Der Benutzer muss nichts tun; die Station belegt weiter einen **Platz** der globalen **Warteschlange**, bis ihr Zeitgeber fällig ist; dann wartet sie als „Fortsetzen“ in der **Warteschlange** und setzt erst fort, wenn ein Platz frei ist. Rang wie „wartet auf Skript“. Geht der Zeitgeber aus (Schalter aus, Senden gescheitert), wird daraus „wartet auf dich“ und der Platz frei. Nach einem Neustart der App wartet keine Station mehr so. Die Zeile zeigt ihn in neutralem Ton mit ↻ als Zeichen (nicht Bernstein wie „wartet auf dich“) und mit dem Chip „ab HH:MM“, wenn die Rücksetzzeit bekannt ist; die Station liegt nicht vorn ([ADR 064](decisions/064-automatisch-fortsetzen.md)). |
| **Warnleiste (Kontingent)** | Leiste unter der Leiste einer Umsetzung, in beiden Reitern, solange mindestens eine nicht fertige Station mit Session am Kontingent pausiert: „Kontingent aufgebraucht.“ mit der Zahl der wartenden Stationen, wie viele um HH:MM automatisch fortsetzen (früheste Rücksetzzeit), wie viele auf dich warten (Schalter aus) und wie viele keine bekannte Rücksetzzeit haben; nach der Rücksetzzeit „Kontingent zurückgesetzt.“ mit denen, die gleich fortsetzen oder noch auf dich warten. Sie trägt denselben Schalter **Automatisch fortsetzen** wie die Leiste. Die Zahlen rechnet die Oberfläche aus den Sessions der Stationen (`quotaWaiting`). Nicht die Kontingent-Warnung des Kontos in der Session-Ansicht ([ADR 064](decisions/064-automatisch-fortsetzen.md)). |
| **Umsetzung** | Ein Plan im Verwalter, als Phasen mit Stationen angelegt über das Werkzeug `implementation_create`; der Verwalter startet jede Station als eigene Session, sobald der Benutzer die Umsetzung gestartet hat (mit **Umsetzung starten** oder ▶ an einer Station), und zeigt den Ablauf als Zeitleiste mit Kartei. Höchstens eine unfertige je Vorhaben. Im Code `implementation` ([ADR 048](decisions/048-umsetzung.md)). |
| **Abbrechen (Umsetzung)** | Beendet eine Umsetzung vorzeitig: Laufende Stationen (auch eine, die auf das Kontingent wartet) werden gestoppt, nichts startet mehr, sie gilt als abgeschlossen, und eine neue Umsetzung im Vorhaben ist möglich; Lanes, Stationen, Verlauf, Sessions und Worktrees bleiben. **Löschen** entfernt danach (oder bei nie begonnener Umsetzung) Lanes, Stationen und Verlauf; Sessions und Worktrees bleiben ([ADR 066](decisions/066-umsetzung-abbrechen-und-loeschen.md)). |
| **Anfrage zum Abbrechen** | Ein Agent bittet per `implementation_cancel` darum, die Umsetzung abzubrechen (und zu löschen); bis der Benutzer auf der Karte „Umsetzung abbrechen?“ bestätigt oder verwirft, startet keine Station. |
| **Phase (Umsetzung)** | Abschnitt einer Umsetzung mit Schlüssel (`1`, `2a`), Titel, Beschreibung und Stationen; in der Oberfläche **Lane** („+ Lane“, „Lane 2 · Titel“). Eine Station heißt überall `<Kennung> · <Stufe>`, etwa „C-5 · Review“ ([ADR 061](decisions/061-constraint-ablaeufe.md), Nachtrag 2026-11-22). Die Reihenfolge kommt aus den Kanten (**Vorgänger und Nachfolger**); nennt kein Plan `after`, leitet der Core sie aus Position und **Welle** ab: Stationen einer Phase in Reihe, die erste jeder Phase hängt an der letzten jeder Phase der Gruppe davor ([ADR 061](decisions/061-constraint-ablaeufe.md)). Im Code und in den Werkzeugen weiter `phases`, `key`. |
| **Lane** | Name der **Phase (Umsetzung)** in der Oberfläche: ein Strang aus Stationen mit Schlüssel und Titel, rein gliedernd; die Reihenfolge kommt aus den Kanten, nicht aus der Lane ([ADR 061](decisions/061-constraint-ablaeufe.md)). |
| **Vorgänger und Nachfolger (Kante)** | Eine Kante sagt: Station B startet erst, wenn Station A angenommen ist. Gespeichert ist sie an B als Vorgänger (`after`, Plan-Kennungen); der Nachfolger (`next`) ist abgeleitet, die Umkehrung von `after`, und wird nie gespeichert. Jede Station hat eine im Plan eindeutige Kennung (`plan_id` in Zeile und Ansicht), die der Verwalter als `<Lane>-<n>` vergibt, nie zweimal dieselbe Nummer; eine `id` in der Eingabe ist nur ein Alias im Aufruf (Nachtrag 2026-11-22). Ausnahme bei `implementation_set_phases`: Nennt eine `id` die Kennung einer Station einer kommenden Lane mit demselben Schlüssel, bleibt es diese Station samt Kennung und Kanten (Nachtrag 2026-11-23). Bereit ist eine nicht fertige Station, deren Vorgänger alle fertig sind; unter bereiten Stationen zuerst höherer Vorrang (`priority`), dann die Planreihenfolge. Zyklus, unbekannte Kennung, Selbstverweis und doppelte Kennung lehnt der Core beim Anlegen und bei einer Plan-Änderung mit einem Satz ab, der die Stationen nennt ([ADR 061](decisions/061-constraint-ablaeufe.md)). |
| **Startstation** | Eine Station ohne Vorgänger (`after` leer): Sie ist sofort bereit und darf parallel zu anderen starten. In einem Plan, in dem irgendeine Station `after` nennt, ist jede Station ohne Angabe eine Startstation ([ADR 061](decisions/061-constraint-ablaeufe.md)). |
| **Kartei** | Die Karte der Station im Fokus neben der Zeitleiste: Kopf mit Zweck (Beschreibung des Agententyps), darunter vier Abschnitte **Ablauf** (Kanten als Chips), **Auftrag** (bei einer Station durch den Benutzer **Anweisung**), **Agent** und **Automatik**; ihre Kopfzeilen zeigen die Werte auch zugeklappt. Bis zum Start ist alles änderbar, danach bis zur Annahme nur **Automatisch fortsetzen** und **Bei Fehler** ([ADR 061](decisions/061-constraint-ablaeufe.md), [ADR 064](decisions/064-automatisch-fortsetzen.md)). |
| **Stufe** | Die errechnete Ebene einer Station im Ablauf (`level`): die längste Kette von Vorgängern bis zu ihr, Startstationen haben Stufe 1; Stationen derselben Stufe sind parallel möglich. Nicht der Stationsname (`stage`, etwa „Review“) ([ADR 061](decisions/061-constraint-ablaeufe.md)). |
| **Gleichzeitige Agenten max.** | Einstellung (Schlüssel `max_agents`, `Settings.maxAgents`, Kategorie Agent): so viele **Plätze** hat die globale **Warteschlange**, also höchstens so viele Agenten startet der Verwalter von selbst; leer = unbegrenzt, sonst mindestens 1, Standard 4. Ein höherer Wert lässt sofort nachrücken, ein niedrigerer beendet nichts ([ADR 068](decisions/068-globale-warteschlange.md)). Zeile in Einstellungen › Agent (Zahlenfeld, leer = unbegrenzt); die Leiste der Umsetzung nennt „Plätze n von m (App)“ mit Füllstand und dem Link „Grenze in den Einstellungen“. Ersetzt **Parallel max.** |
| **Parallel max.** | Altbegriff: Grenze gleichzeitig aktiver Stationen je Umsetzung (Feld `max_parallel`, [ADR 061](decisions/061-constraint-ablaeufe.md)). Entfallen mit Migration 29; es gilt nur noch **Gleichzeitige Agenten max.** app-weit. Ein Planer-Werkzeug, das das Feld noch übergibt, bekommt einen Satz, der die Einstellung nennt ([ADR 068](decisions/068-globale-warteschlange.md)). |
| **Platz** | Was die Grenze **Gleichzeitige Agenten max.** zählt: eine Session mit Status „startet“ oder „läuft“, eine Session, die nach ihrer Antwort auf einen Subagenten oder ein Skript wartet (danach macht der Agent von selbst weiter), ein Anspruch im Gang (Countdown einer Station, Start, Zustellung, Fortsetzen) und eine Station, die **setzt automatisch fort**, bis ihr Zeitgeber fällig ist (danach wartet sie als „Fortsetzen“); eine Station, die neu am Kontingent pausiert, hält ihren Platz, bis der Verwalter über den Zeitgeber entschieden hat. Nicht gezählt: Rückfrage offen, pausiert ohne Zeitgeber, fertig, Fehler, abgebrochen, neu und ruhende Prozesse ([ADR 068](decisions/068-globale-warteschlange.md)). Die Leiste der Umsetzung zeigt die belegten Plätze der ganzen App als Kästchen; über der Grenze (nach einem eigenen Start oder dem Senken der Grenze) gelb mit „über der Grenze“. Eine Session, deren zugestellte Nachricht auf einen Platz wartet, zeigt „Nachricht wartet · Platz n“ (in der Sidebar kurz „✉ Platz n“). |
| **Warteschlange** | Global über alle Vorhaben: was der Verwalter von selbst starten würde und auf einen freien **Platz** wartet — bereite Stationen mit **Automatisch starten**, Stationen vor dem Neustart nach **Bei Fehler**, Nachrichten der Session-Werkzeuge an ruhende Sessions (Posteingang, auch die erste Nachricht einer per `verwalter_open_session` geöffneten Session) und fällige Fortsetzungen nach dem Kontingent (sie halten ab Fälligkeit keinen Platz mehr und warten seit diesem Zeitpunkt). Reihenfolge: **Priorität des Vorhabens**, dann der Vorrang der Station (`priority`; Nachrichten und Fortsetzen 0), dann wer früher wartet; kein Altern; eine Nachricht an den Master einer laufenden Umsetzung rückt vor die Wartenden ihres eigenen Vorhabens (nie vor einen Wartenden eines anderen Vorhabens, der vor dem besten ihres Vorhabens steht). Plätze 1-basiert über die ganze App (`queuePosition`, an der Umsetzung `queued` = wartende Stationen dieser Umsetzung, Liste per `agent_queue`). Ein Durchgang rückt nach, sobald ein Zug endet, eine Station fertig meldet, ein Zeitgeber ausgeht, die Grenze steigt oder etwas zu warten beginnt. Eine **eigene Nachricht** an eine ruhende Session wartet ebenfalls (Taiga-Story 190). Er entscheidet über die Meldungen seiner Stationen mit dem Werkzeug `implementation_review_station`; Stationen sprechen nur mit ihm (`verwalter_send_message_to` an andere und `verwalter_open_session` sind für Stationen gesperrt). `masterMissing`: Die Session ist gelöscht oder steht im Fehler; eine Kontingent-Pause ist kein Ausfall. Oberfläche: Der Kopf der Umsetzung zeigt „Master: #N Name · ändern“ (`MasterPicker`); „ändern“ öffnet die Sessions des Vorhabens, Stationen stehen gesperrt darin, dazu „Neue Session als Master“; bei `masterMissing` steht darunter eine Warnleiste. In der Leiste steht die Umsetzung als eine Zeile unter der Master-Session (◆ an deren Zeile), darunter nur ihre Stationen, die dich brauchen (fragt dich, wartet auf dich, Fehler); ohne Master, bei ausgefallenem oder gelöschtem bleibt sie im Vorhaben ([ADR 070](decisions/070-master-session.md)). |
| **Gemeldet** | Zustand einer Station (`reported`): Sie hat mit `implementation_complete_station` an ihren Master gemeldet (Betreff `result`, Bericht `note`, `fix_needed`) und der Master hat noch nicht entschieden; die Station wartet auf ihn, nicht auf den Benutzer. Der Master entscheidet erst, wenn ihr Zug beendet ist (Abgabe, Fehler oder Abbruch; eine Pause nicht). Sind seine Rückgaben verbraucht, steht sie auf „wartet auf dich“. Oberfläche: eigene hellblaue Farbe („gemeldet“, in der Dringlichkeit wie „läuft“), in Zeile, Zeitleiste und Kartei; die Kartei zeigt den Abschnitt „Bericht an den Master“ (Betreff, Notiz, Befund, „zurückgegeben n von 3“) und „Wartet auf den Master #N“ ([ADR 070](decisions/070-master-session.md)). |
| **Läuft wieder** | Eine fertige Station, deren Session nach der Annahme wieder aktiv ist (der Master oder der Benutzer schrieb ihr): Sie bleibt `done`, `StationView::live` zeigt den Zustand der Session; Zeile, Kartei und Leiste sagen „fertig · läuft wieder“, „fertig · fragt dich“, „fertig · pausiert“ oder „fertig · Fehler“ ([ADR 070](decisions/070-master-session.md)). |
| **Grund einer Pause** | `StationView::pause`: `quota` mit der Rücksetzzeit („Kontingent bis HH:MM“, ohne Zeit „Kontingent“) oder `other` (vom Benutzer pausiert oder nach dem Neustart der App, kein Chip). |
| **Rückgabe** | Der Master gibt eine Meldung mit einer Nachricht an die Station zurück (`answer: "return"`): Die Meldung entfällt, `returns` zählt hoch, die Station arbeitet weiter und meldet erneut. Höchstens dreimal durch den Master (`returnsLeft`), danach nimmt der Benutzer an oder gibt zurück, ohne Grenze (Befehle `implementation_accept_station`, `implementation_return_station`). Oberfläche: Die Kartei zeigt „n von 3“; bei erschöpften Rückgaben („wartet auf dich“) stehen dort „Annehmen“ und „Zurückgeben“, Zurückgeben bleibt gesperrt, solange die Nachricht leer ist oder nur Leerzeichen enthält ([ADR 070](decisions/070-master-session.md)). |
| **Als fertig markieren** | Der Benutzer beendet eine Station des Agenten von Hand, die der Ablauf nicht weiterbringt: im Fehler ohne anstehenden Neustart (auch mit Startfehler) oder mit pausierter Session ohne scharfen Zeitgeber, mit oder ohne Meldung (Befehl `implementation_mark_station_done`, Knopf „Als fertig markieren …“ in der Kartei und in den Popups `error` und `paused`, Dialog mit dem Feld „Ergebnis“). Wirkt wie eine **Annahme** ohne Meldung und ohne Fix-Runde; die Session bleibt, die Station zeigt `done`, der Master bekommt das Ereignis „Von Hand fertig“ ([ADR 048](decisions/048-umsetzung.md), [ADR 070](decisions/070-master-session.md), [ADR 071](decisions/071-dashboard.md)). |
| **Freigeben** | Der Master gibt eine Station „durch dich“, die an der Reihe ist, frei (`answer: "release"`): setzt nur die Marke `released_at`; die Station bleibt beim Benutzer („Erledigt“ wie bisher). Oberfläche: Die Kartei trägt die Marke „✓ vom Master freigegeben“, die Zeitleiste „✓ freigegeben“ ([ADR 070](decisions/070-master-session.md)). |
| **Dashboard** | Ansicht „Aufgaben“, auf der die App startet: die **Karten** dessen, was auf den Benutzer wartet, daneben die Abläufe (Umsetzungen) und die aktiven Sessions ohne Station. Der Kern bildet sie aus seinen Zuständen (`dashboard::build`, Befehl `dashboard_get`), die Oberfläche rechnet nichts nach. Beim Gast kommen die Karten, Abläufe und Sessions der Vorhaben dazu, die er an einem Host hält; gefiltert hat der Host. Eine Arbeitsliste, kein KPI-Dashboard. Oberfläche: Eintrag „Dashboard“ oben in der Leiste mit der Zahl aller Karten, in der Mitte die Karten (über gespeicherte Schalter geschachtelt in der festen Reihenfolge Gruppe → Vorhaben → Art, Vorhaben nach Priorität, jede Gruppe einklappbar; filterbar auf Karten, die einen Agenten anhalten), rechts die Abläufe und die Sessions ohne Ablauf, lokale und entfernte gemeinsam geordnet: zuletzt aktiv zuerst, fertige Abläufe am Ende. Karten, Abläufe und Sessions eines Vorhabens, das der Gast an einem Host hält, tragen die Marke „entfernt“ mit dem Namen des Hosts ([ADR 071](decisions/071-dashboard.md)). |
| **Karte (Dashboard)** | Eine Zeile der Aufgabenliste: etwas, das auf den Benutzer wartet (Rückfrage, Rechte-Abfrage, Antwort, Fehler, Pause, Plan-Änderung, „durch dich“ …), mit stabiler Kennung und `since`. Nicht zu verwechseln mit dem **Vorhaben** („eine Aufgabe“) und mit der Karte einer Station in der Kartei der Umsetzung; die Überschrift der Ansicht heißt „Aufgaben“. Eine Karte verschwindet, wenn der Zustand dahinter endet; Karten einer Session ohne Station auch mit **Gelesen**. Ein Klick auf eine Karte öffnet ihr **Popup** ([ADR 071](decisions/071-dashboard.md)). |
| **Popup (Dashboard)** | Der Dialog einer Karte: Er zeigt die Sache mit den Bausteinen von Chat und Umsetzung (Rückfrage, Kasten, Plan-Änderung, Bericht, Master-Wahl, Antwortfeld …), und der Benutzer erledigt sie dort; links „Session öffnen“ bzw. „Umsetzung öffnen“, Esc schließt nur das Popup. Es schließt sich auch, wenn der Kern die Karte nicht mehr liefert ([ADR 071](decisions/071-dashboard.md)). |
| **Aufforderung im Chat** | Eine Karte des Dashboards, die der Chat ihrer Session zeigt: als Leiste oben, als Rahmen an der letzten Antwort und als Hinweis am Eingabefeld; sie verschwindet mit der Karte ([ADR 071](decisions/071-dashboard.md)). |
| **Einordnung (Dashboard)** | Am Zugende einer Session ohne Station ordnet ein kleines Modell die letzte Textantwort ein: `asks` (fragt), `requests` (bittet um eine Handlung außerhalb), `done` (fertig), mit einem Einzeiler für die Karte. Läuft in einem eigenen Thread ohne Sperre und wird nur gespeichert, wenn kein neuer Zug dazwischenkam; ohne sie (Modell „Aus“, Fehler, Zeitlimit) bleibt die Karte „Antwort liegt vor“. Einstellung „Modell der Einordnung“, Standard Haiku ([ADR 071](decisions/071-dashboard.md)). |
| **Gelesen** | Aktion auf einer Session-Karte des Dashboards (Befehl `dashboard_dismiss`): setzt `card_dismissed_at` auf jetzt; die Karten der Session (Antwort, Fehler, Pause) sind weg, bis ein neuerer Zustand entsteht. Die Session zu öffnen ist nicht „Gelesen“ und lässt die Karte stehen; im Popup einer Antwort, eines Fehlers oder einer Pause der Knopf „Gelesen“ ([ADR 071](decisions/071-dashboard.md)). |
| **Wartet auf Master** | Zustand eines Ablaufs im Dashboard (`waitsForMaster`): eine Station hat gemeldet oder ohne Meldung abgegeben, der Master entscheidet; es gibt dafür keine Karte für den Benutzer ([ADR 071](decisions/071-dashboard.md), [ADR 070](decisions/070-master-session.md)). |
| **Eckiges Symbol** | Zustandssymbol einer Umsetzung in Leiste und Kopf (`StatusIcon` mit `shape="square"`): dieselbe Formbedeutung und dieselben Farben wie das runde Symbol der Sessions und Stationen (läuft: gefüllt mit Hof, wartet auf dich: Rahmen mit Kern, Fehler: Rahmen mit Ausrufezeichen, pausiert: zwei Balken, fertig: Haken, neu: gestrichelt); die Farbe folgt wie bisher `urgency` der Umsetzung ([ADR 070](decisions/070-master-session.md)). |
| **Lagebericht** | Programmatischer Stand einer Umsetzung als Text: Lanes, ihre wartenden Stationen in der globalen Warteschlange, Startstationen, Stationen samt Stufe, Vorgängern und Nachfolgern, offene Frage, Plan-Änderungen, geänderte Dateien; hängt an jeder Rückfrage und steht hinter dem Knopf „Lagebericht“. |
| **Rückfrage (Umsetzung)** | Reguläre Session im Vorhaben mit dem Lagebericht als Anhang, zum Lesen, Erklären und Umplanen; ändert keinen Code — eine Regel für den Agenten, keine Sperre. Nicht zu verwechseln mit der Rückfrage des Agenten (AskUserQuestion). |
| **Plan-Änderung** | Vorschlag aus einer Session über `implementation_set_phases` mit der vollständigen Liste der kommenden Phasen oder über `implementation_edit` als **Delta**; wirkt erst nach „Übernehmen“ auf der Karte „Plan ändern?“; neu, vorgezogen, geändert, entfallen. Die Einstellungen einer Station mit der Marke `edited` gehen auf die neue Station mit gleichem Phasenschlüssel, gleichem Stationsnamen (`stage`) und gleicher laufender Nummer dieses Namens über, soweit der Planer sie nicht nennt; gerechnet wird beim Übernehmen. |
| **Plane Vorhaben** | Knopf der Eingabeleiste: Der Verwalter setzt selbst die erste Nachricht eines Planungszugs, den festen Planungs-Prompt (`implementation::plan::plan_prompt`) mit dem Text des Felds als Auftrag; der Verlauf zeigt nur den Auftrag. Der Prompt verlangt das Ergebnis über `implementation_create`, nennt **Lane** und **Station**, das Muster Test, Umsetzung, Review, PR und die Konfiguration je Station (Typ, Prompt, Modell, Denkaufwand) und führt keine Feldnamen des Schemas. Gesperrt bei leerem Feld, bei offener Rückfrage und außerhalb der Betriebsart Claude (nur dort hat die Session die Werkzeuge des Verwalters). Befehl `session_plan_vorhaben`; den Aufruf von `implementation_create` prüft der **Wächter** ([ADR 062](decisions/062-plane-vorhaben.md)). |
| **Planungszug** | Der Zug einer Session, den „Plane Vorhaben“ begonnen hat; sein Wächter liegt nur im Speicher (`SessionState::plan_guard`, gelesen vom Wächter selbst; `SessionRegistry::is_planning_turn` hat keinen Aufrufer mehr). Jeder neue Zug setzt ihn neu, die Antwort auf eine Rückfrage und eine Erinnerung des Wächters lassen ihn stehen; nach einem Neustart der App ist er weg ([ADR 062](decisions/062-plane-vorhaben.md)). |
| **Wächter** (Plane Vorhaben) | Prüft am Ende eines abgeschlossenen Planungszugs, ob der Agent `mcp__verwalter__implementation_create`, `mcp__verwalter__implementation_set_phases` oder `mcp__verwalter__implementation_edit` aufgerufen hat (nur der Werkzeugname zählt, nicht das Ergebnis; `implementation_edit` zählt mit, weil `implementation_create` in einem Vorhaben mit unfertiger Umsetzung immer ablehnt). Fehlt der Aufruf, schickt er höchstens zweimal die feste Erinnerung `PLAN_REMINDER_TEXT`, danach steht im Verlauf der Hinweis **Kein Plan im Umsetzungstool** mit **Erneut** (neuer Planungszug mit demselben Auftrag) und **Trotzdem weiter** (erledigt den Hinweis; die Prüfung endete schon mit ihm); Befehl `session_plan_settle`. Entscheidung `implementation::plan::guard_step`, Fortschritt am Zugende `advance_guard` ([ADR 062](decisions/062-plane-vorhaben.md)). |
| **Prompt-Cache** | Claude hält den bisherigen Verlauf einer Session nach jeder Antwort eine Zeit lang bereit (gemessen 1 Stunde, sonst 5 Minuten); die nächste Nachricht liest ihn dann günstig, statt ihn neu zu schreiben. Gilt nur für ein Modell; abgelaufen, nach einem Modellwechsel oder nach einer Zusammenfassung ist er „kalt“. Im Code `prompt_cache` ([ADR 033](decisions/033-warnhinweise.md)). |
| **Hinweis (Verlauf)** | Zeile im Chat-Verlauf, die festhält, was Claude oder der Verwalter getan hat, ohne Nachricht zu sein: Zusammenfassung, Modellwechsel, Modell-Ausweichen, Moduswechsel, Hinweis von Claude Code, Abschluss einer Antwort. Im Code `ChatEntry::Notice` ([ADR 033](decisions/033-warnhinweise.md)). |
| **Modell-Ausweichen** | Claude wechselt nach einer Markierung durch den Sicherheitsfilter selbst auf ein anderes Modell; die Eingabeleiste zeigt das Ersatzmodell, bis der User ein Modell wählt oder der Agent neu startet. Im Code `fallback_model` ([ADR 033](decisions/033-warnhinweise.md)). |
| **Zusammenfassung (Verlauf)** | Claude ersetzt den bisherigen Verlauf durch eine Kurzfassung, von Hand (`/compact`) oder automatisch kurz vor vollem Kontext; danach kennt der Agent Einzelheiten nur noch aus der Kurzfassung. Nicht zu verwechseln mit dem TL;DR. |
| **Compact durch den Verwalter** | Eine ruhende Master-Session einer unfertigen Umsetzung, deren Kontext über „Master zusammenfassen ab … Tokens“ liegt (Standard 150 000), bekommt `/compact` als eigenen Zug. Keine Eingabe: Dashboard und Ungelesen bleiben; der Chat zeigt „Verlauf zusammengefasst · automatisch durch den Verwalter“ ([ADR 070](decisions/070-master-session.md)). |
| **Werkzeug-Detail** | Eingabe und Ausgabe eines Werkzeug-Aufrufs des Hauptagenten, gespeichert je Aufruf und erst beim Aufklappen der Zeile im Chat geladen; Eingabe höchstens 32 KiB, Ausgabe höchstens 128 KiB, Kürzung wird angezeigt ([ADR 042](decisions/042-werkzeug-details.md)). |
| **Ohne Fundstelle** | Angabe in einer Antwort des Agenten (Pfad, Datei:Zeile, Zahl ab zwei Ziffern), die in keiner Werkzeug-Ausgabe derselben Antwort und nicht in der Nachricht des Nutzers vorkommt; im Verlauf gepunktet unterstrichen ([ADR 036](decisions/036-ohne-fundstelle.md)). |
| **Einstellungs-Kategorie** | Eine der vier Gruppen in der Leiste links auf der Einstellungsseite: Allgemein, Agent, Skills & Umgebung, App. Jede enthält Abschnitte mit Zeilen; der Katalog `settingsCatalog.ts` legt fest, was wohin gehört ([ADR 057](decisions/057-einstellungen-kategorien-und-suche.md)). |
| **Portable** | Die lose `verwalter.exe` ohne Installer; ein Update ersetzt sie am selben Pfad ([ADR 041](decisions/041-app-update.md)). |
| **Prüfsumme** | SHA-256 einer Release-Datei, von GitHub je Datei genannt; ohne Treffer wird nichts installiert ([ADR 041](decisions/041-app-update.md)). |
| **Schreib-Ordner** | Ordner, in dem eine Session tatsächlich schreibt: ihre benutzten Ticket-Worktrees und der Haupt-Checkout, wenn sie dort Dateien geändert hat ([ADR 037](decisions/037-parallele-sessions.md)). |
| **Master-Ordner** | Frei gewählter Ordner mit den Originalen von Skills, Befehlen, Ausgabestilen und `CLAUDE.md`; der Verwalter vergleicht `~\.claude` damit und spiegelt auf Klick ([ADR 038](decisions/038-umgebung.md)). |
| **Spiegeln** | Kopiert aus dem Master-Ordner, was dort neuer ist oder lokal fehlt; löscht nie ([ADR 038](decisions/038-umgebung.md)). |
| **Umgebung des AppImage** | Die Umgebungsvariablen, die der Start des Linux-AppImage setzt und deren Einträge in das Bündel unter `/tmp/.mount_…` (`$APPDIR`) zeigen: `LD_LIBRARY_PATH`, `PATH`, `XDG_DATA_DIRS`, `PYTHONHOME`, die Pfade von GTK, GStreamer und Qt und weitere; den ursprünglichen Wert hängt der Start jeweils hinten an. Der Kern gibt sie nicht an Kindprozesse weiter: `processes::command` (das Terminal: `processes::pty_command`) nimmt jeden Eintrag unter `$APPDIR` heraus, bleibt nichts übrig, entfällt die Variable; sonst laden `node`, `python3`, `curl` und `git` die älteren Bibliotheken des Bündels und brechen ab. `APPDIR`, `APPIMAGE`, `OWD` und `ARGV0` bleiben. Nur die eigene Exe aus dem Bündel (Betriebsarten Autark und Codex) behält die Umgebung, denn sie ist mit den Bibliotheken des Bündels gebaut. Ohne `APPDIR` (Windows, macOS, `pnpm tauri dev`) ändert der Kern nichts. |
